## 1. P1-7：移动端内核配对校验下沉到模型层（唯一代码项）

### 现状

入口校验已经存在且正确，但只覆盖 HTTP API：

- [`app/main.py:297`](../app/main.py) `_check_mobile_target()`：`target_os ∈ {android, ios}` 且 `kernel != fp-chromium` → 400。
- [`app/main.py:302`](../app/main.py) 同上；更新路径 [`app/main.py:667`](../app/main.py) 按「改后的生效值」判断。
- [`app/launcher.py:135`](../app/launcher.py) 启动期再兜一次底。

缺口：

1. **`ProfileCreate` 模型本身不校验**。任何绕过 `main.py` 的调用方（MCP 工具、脚本、后续新增的入口）都能构造出 `kernel=camoufox, target_os=android` 的对象，直到启动才失败——失败点离错误来源很远。
2. `ProfileUpdate` 是「只改一个字段」的语义，模型层无法单独判断（需要与库中现值合并），这条**不适合**下沉，保持入口校验即可。
3. 清单建议的 `@validator` 写法是 Pydantic v1 语法，本项目用 v2（`model_validator`）。

### 方案

只给 `ProfileCreate` 加跨字段校验，`ProfileUpdate` 不动：

```python
# app/models.py
from pydantic import model_validator

class ProfileCreate(BaseModel):
    ...
    @model_validator(mode="after")
    def _mobile_kernel_pairing(self):
        if self.target_os in ("android", "ios") and self.kernel != "fp-chromium":
            raise ValueError("移动端目标 OS（android/ios）仅支持 fp-chromium 内核")
        if self.target_os == "android" and self.browser not in (None, "chrome"):
            raise ValueError("Android 仅支持 chrome 浏览器口径")
        return self
```

要点：

- 错误文案与 `main.py` 保持一致，避免同一个错误出现两种措辞。
- 品牌存在性（`manufacturer` 必须在机型库）**不下沉**：机型库是运行期数据，模型层不应依赖数据文件；保持 `_check_mobile_manufacturer()`。
- `browser` 的 Android 约束在 [`main.py:316`](../app/main.py) `_check_mobile_browser()` 已有等价校验（复用 `_normalize_browser()`），模型层这条是双保险，成本为零，保留。
- 项目用 Pydantic **2.13.5**，`@validator`（清单原文的 v1 写法）不可用，必须 `model_validator(mode="after")`。

### 验证

- 新增 3 条数据层断言（`scripts/mobile_test.py`，不启动浏览器）：非法组合 `ValueError` / 合法组合通过 / 错误文案与 API 一致。
- 跑 `scripts/mobile_test.py`（251 → 254）与一次 API 冒烟（`phase4_test.py`）。

## 2. P2-9：补「整机链路」自动化

### 现状

已有的三层验证各自覆盖一段，但没有一条用例把**用户实际路径**串起来：

| 层 | 脚本 | 覆盖 | 盲区 |
| --- | --- | --- | --- |
| 数据层 | `scripts/mobile_test.py`（251） | 指纹生成、机型库自洽、旧结构兜底 | 不碰浏览器 |
| 真机级 | `scripts/mobile_launch_verify.py`（158 / 198 / 213） | 页面内逐项读数 | 直接建会话，**跳过 API 与数据库** |
| 端到端 | `scripts/test_mobile_end_to_end.py` | 创建 → 启动 → 读页面 | 只有冒烟级读数，未接输入代理/安全区/传感器 |

清单里的 CreepJS/Pixelscan 用例**不建议照抄**：

- 依赖外网与第三方页面结构，CI 不稳定；
- 分数是黑盒，回归失败时无法定位到具体面；
- 检测站自身会更新，断言阈值无法长期维护。

### 方案：用「本地检测站」替代第三方站点

新增 `scripts/mobile_e2e_test.py`，起一个本地 HTTP 页，把检测站最常用的**判假信号**一次性读全，并与启动返回的指纹逐项比对：

```
API 建环境（android / ios × safari/chrome_ios）
  → 启动（拿 ws_endpoint / ws_endpoint_direct）
  → Playwright 经代理连接（验证代理链路本身）
  → 本地检测页读取：
      · UA / platform / UA-CH / 屏幕 / DPR / 视口
      · WebGL 渲染器 + 扩展集 + MAX_*
      · canPlayType 矩阵
      · 传感器事件计数与采样间隔中位数
      · env(safe-area-inset-*)（cover / 非 cover 两页）
      · 输入序列（Playwright mouse.click → 页面记录 pointerdown 的 pointerType）
  → 断言「页面读数 == 环境指纹」，任何不一致即失败并打印差异字段
```

判据全部是**确定性比对**（指纹 vs 页面），不依赖第三方打分。第三方站点留给人工抽查（清单里的原始意图），在文档里写成「可选人工步骤」。

预计 20~25 项断言，跑一轮约 1 分钟。放进 `scripts/` 而非 `tests/`，与现有脚本风格一致（仓库当前没有 `tests/` 目录）。

### 验证

- 三种口径各跑一次全绿。
- 故意改坏一个字段（如临时把 `renderer` 改成宿主值），确认脚本能报出具体差异字段——避免「永远绿」的空断言。

### 实施中发现的细节

1. **`about:blank` 不能用于视口断言**：没有 `<meta viewport>` 时移动仿真按 980px 虚拟视口排版（与真机一致），`innerWidth` 读到 980。整机链路脚本改用声明了 `width=device-width` 的本地页面，这条也写进了 FAQ。
2. **`getBattery()` 必须 await**：首版探针只判 `'getBattery' in navigator` 并读 `level`，得到的是 `null`；改为 `await navigator.getBattery()` 后与指纹 `battery.level/charging` 完全一致。
3. **反向验证的写法**：改存储指纹不会让脚本报错（注入层读的是同一份），必须只改注入侧的 `derive_spec` 输出，才能证明断言真的在比对两个来源。
