# 移动端大厂检测对抗优化方案

> **方法**：真实运行态实证（探针读数）→ 与真机口径逐项比对 → 按「检测收益 / 误伤风险」排序修复（P0 直接落地，其余给出设计与验证方法）。
> **口径来源**：MDN Browser Compat Data / caniuse（2026-10）、Chromium 源码构建开关（`enable_pdf=!is_android`）、liarjs.dev、本项目既有报告（[`Chrome61-IPA检测机制分析.md`](Chrome61-IPA检测机制分析.md)、[`Chrome61-IPA补丁方案.md`](Chrome61-IPA补丁方案.md)、[`移动端真实指纹库.md`](移动端真实指纹库.md)）。
> **覆盖的检测面**：极验 / 网易易盾 / 顶象 / 腾讯天御（行为 + 环境取证）、BrowserScan / FingerprintJS / CreepJS（属性面）、Cloudflare / Akamai / DataDome / HUMAN / Kasada / reCAPTCHA（行为 + 网络层）。
> **不变量**：不改动已存指纹数据；不改动既有条目的屏幕 / DPR 值；新机型必须为真实规格；移动端 target_os 仅支持 fp-chromium 内核。

| 项 | 说明 |

**实现要点（内核实证）**：

- **时序硬约束**：CDP 虚拟传感器必须在页面注册监听**之前**下发——传感器请求一旦在「无传感器」状态定型，之后启用覆盖也不再派发事件（实测）。挂载点因此选在目标 attach 的 `waitForDebuggerOnStart` 暂停期内，早于首个文档脚本执行。
- **类型映射**：`accelerometer`→`accelerationIncludingGravity`、`linear-acceleration`→`acceleration`、`gyroscope`→`rotationRate`（输入 rad/s、事件读回 deg/s）、`relative-orientation`→`deviceorientation`、`absolute-orientation`→`deviceorientationabsolute`；`gravity` 无经典事件消费（不启用）。
- **虚拟传感器是浏览器进程级全局对象**：其他目标再次 enable 返回 `The specified sensor type is already overridden`，读数推送对所有页面/iframe 生效——与真机一致（同一设备的所有页面共享同一份传感器数据），因此只运行一条读数循环。
- **读数形状**：必须嵌套 `reading:{xyz:{x,y,z}}` / `reading:{quaternion:{x,y,z,w}}`（顶层 `xyz/quaternion` 报 `Invalid parameters`）；四元数按 `R = Rz(α)·Rx(β)·Ry(γ)` 生成，与内核反解严格一致。
- **事件节奏**：`devicemotion` 由内核 60Hz 轮询派发（`interval=16`，读数更新即改变内容）；orientation 事件「每读数变化派发一次」→ 读数循环按 60Hz（16.7ms ±20%）排程，交替用绝对时刻而非「发完再睡」，五类读数并发下发（详见 §2.16）。抖动是刻意的：严格定频会让「事件内容变化」呈精确周期性。
- **安全上下文**：非安全上下文（如 `http://probe.test`）不派发传感器事件（内核行为与真机一致）——verify 的传感器探针必须跑在 `127.0.0.1` 本地服务页上。

- **看门狗**：连接建立后启动后台任务，每 10s 发一次 `Target.getTargets` 探活（命令超时 5s）；读循环结束/异常（含对端干净关闭）**立即**标记通道失效，1s 内进入重连；重连指数退避（1s → 30s，上限），成功后回到 10s 探活。覆盖对端关闭、半开连接（探活超时）、连接被替换三种断线形态。

- **回归（`mobile_launch_verify.py` 内置，4 项）**：断开通道 → 断线期间新开标签页读到宿主值（复现事故形态：`touch=0` / `coarse=false` / `plat=MacIntel`）→ 看门狗自动重连（计数 +1、状态回 `ok`）→ 断线期间新标签页与断线前已存在页面全部回到移动端仿真（`touch=5` / `coarse=true` / `plat=iPhone|Android`）。

**对检测平台的三条探针校准建议（WebAudio 项）**：

1. 现探针不具区分度：原生 Chrome 亦判「人工加噪」——`-35 dB` 阈值相对该探针信号自身的频谱不可达（三角波三次谐波 + 800 Hz 二极点低通仅 -12 dB/oct，叠加 512 点无窗 DFT 泄漏）。
2. 真噪声判据应测**静音渲染**：`new OfflineAudioContext(1, 4096, 44100).startRendering()` 的输出缓冲在任何真机/原生 Chrome 上恒为精确 0（实测平均绝对偏差 = 0.0），而「在 `getChannelData` 注入随机微噪」的工具会留下平坦底噪——零知识判据，无需基线阈值。
3. 若保留现探针：至少给 DFT 加 Hann 窗，判据改为截止带**平坦度**（多频点方差）而非绝对能量比，并用原生浏览器基线校准阈值。

**背景**：检测站对「声明 iOS、引擎却是 V8」有四条**互相独立**的判据，任一条命中即判假。本轮逐条对齐 WebKit，并补上 iPhone 屏的硬件级判据。

**实现要点（`app/mobile_cdp_injector.py`）**：

- **Error Proxy 的栈改写**：`Object.getOwnPropertyDescriptor(Error.prototype,'stack').get.call(err)` 取原始 V8 栈 → 逐帧解析（正则取 `file:line:col`）→ 拼回 `fn@loc`。**必须丢弃 Proxy 陷阱自身的合成帧**：`construct`/`apply` 陷阱会往栈里压 `Object.construct@<anonymous>:294:56`，真机 JSC 不存在这类帧，且会让**每个** Error 的 `line`/`column` 变成同一个常量（首次实测即踩到，`errStackHead` 恒为 `Object.construct@<anonymous>:281:56`）。过滤条件 = 帧名匹配 `/^Object\.(construct|apply)$/` 且文本含 `<anonymous>`。
- **`line`/`column` 只在显式构造时可得**：`new Error()` 走 `Error` 全局的 `construct` 陷阱，能补上真实位置（实测页面上下文 `probe@<anonymous>:2:29`，`line: 2, column: 29`）；但**引擎内部抛出的 `TypeError`/`SyntaxError` 在 C++ 侧直接创建**（V8 的 `Factory::NewTypeError`），不经过 `Error` 全局，`Object.getOwnPropertyDescriptor(TypeError.prototype,'message')?.get` 无法被 JS 拦截变真 → `isV8ErrorSyntax` 15 分**不可修**，属引擎层残余。
- **Proxy 透明性**：`Error.name` / `Error.length` 用 `defineProperty` 重设以保持原生形态（WebKit 实测两者均为 `[writable:false, enumerable:false, configurable:true]`，与 `defineProperty` 默认值一致）。`instanceof`、子类化（`class Sub extends Error`）、`Error.length === 1` 均验证通过。
- **`Error.captureStackTrace` 不抹除**：WebKit `Source/JavaScriptCore/runtime/ErrorConstructor.cpp:52` 以 `JSC_NATIVE_FUNCTION_WITHOUT_TRANSITION` 注册了同名静态方法——检测站「V8 专有」文案已过时，与 `SharedWorker` 属同一类陈旧判据。
- **Display P3 用 CDP 而非 JS 改 `matchMedia`**：`Emulation.setEmulatedMedia {media:"screen", features:[{name:"color-gamut",value:"p3"}]}` 在内核上原生生效（实测立即生效、同页导航后保持、同进程 iframe 继承），**但不跨页面**——新 page 目标回到 sRGB。故页面路径（`_apply_device_emulation`）与 OOPIF 路径（`_attach_frame`）**各自下发**，且每次页面级仿真都重发。JS 改 `matchMedia` 会破坏原生函数形态，不采用。
- **`Intl.v8BreakIterator` 需要单独路径，且**页面与 Worker 都要删**：它挂在 `Intl` 对象自身（既非 window/self 成员也非原型成员），通用「按名删除」循环覆盖不到；且 V8 个别构建会在脚本执行期惰性装回，故加 `setTimeout(..., 0)` 兜底补删一次。**Worker 里同样存在**（实测 `Intl.v8BreakIterator` 为真），只删页面会留下「页面 `false`、Worker `true`」的跨上下文矛盾——检测站起一个 Worker 读一次即可命中。Worker 侧有两条链路需同时补：`_WORKER_PATCH_TEMPLATE` 的按名删除循环，以及首脚本前的 `beforeScriptExecution` 插桩断点（`build_worker_drop_patch`，且 `_attach_worker` 需把页面表 `removeGlobals` 里的 `v8BreakIterator` 合并进断点删除清单——两张表原本互不交叉）。

**已知不可修残余（引擎层边界，已写入代码注释）**：

| 项 | 分值 | 原因 |
| --- | --- | --- |
| `isV8ErrorSyntax`（`Error.prototype.message` 为访问器） | 15 | V8 内部抛出的异常在 C++ 侧创建，不过 `Error` 全局陷阱 |
| `'chrome' in window` | 10 | `Object.getOwnPropertyDescriptor(window,'chrome').configurable === false`，`delete` 返回 false——内核级不可删除（既有文档已记载） |

**回归（`scripts/mobile_launch_verify.py`，新增 14 项）**：JSC 栈格式 / 原生 `toString` 多行形态 / 用户函数不被改写 / `prepareStackTrace` 缺席 / `Error.prototype.message`·`name` 数据属性 / own `line`·`column` 数据属性 / 栈首帧无 Proxy 合成帧 / Proxy 透明性（`instanceof`·子类化·`name`·`length`）/ `captureStackTrace` 保留 / `v8BreakIterator` 缺席 / Worker 内 `v8BreakIterator` 同样缺席 / `webkitTemporaryStorage`·`PersistentStorage` 缺席 / `(color-gamut: p3)` 为真。

### 2.13 触摸拖拽剖面：速度曲线 / 压力曲线 / 原生 fling（P2-4，2026-10-20 第八批）

**背景**：P2-4 原判「触摸拖拽不含系统惯性（fling）与压力曲线」。实测后一半判断已过时、前一半成立——分述如下。

**fling 是内核原生的，不需要仿真**。CDP `Input.dispatchTouchEvent` 派发的 touchmove 带真实时间戳，内核按松手瞬间的速度自己发起原生 fling 动画。实测（fp-chromium 148，8 帧 300px 行程，松手后 0.8s 的 `scrollY` 增量）：

| 帧间隔 | 松手后位移 |
| --- | --- |
| 50ms | 0px |
| 20ms | +219px |
| 12ms | +205px |
| 4ms | +84px |

本模块的帧间隔刻意落在 14ms（60fps 档），与真机拖拽同档，松手即带惯性。verify 断言直接锁定这一行为（`fling >= 20`），防止后续改动把它调进「太慢无惯性」的档位。

**压力/接触面积是真机有、旧实现没有的**。`Input.dispatchTouchEvent` 的 `touchPoints` 原生支持 `force` / `radiusX` / `radiusY`，直接透传给页面（`rotationAngle` 被接受但读回恒 0，故不设）。旧实现固定 `force=1.0`、`radius=1.0`，页面上读到的是全程恒定的压力序列——真机手持按压的 force 会随按到峰值、抬指前放松起伏。

**速度剖面**：旧实现每帧等距，`dy` 序列完全平坦。现按「前一半帧线性加速（0.15 → 1.0 倍）→ 其后匀速」分配每帧位移。

| 实现细节 | 取值 | 原因 |
| --- | --- | --- |
| 斜坡形状 | 线性，`0.15 + 0.85 * i/(ramp-1)` | 二次曲线在长步数下前若干帧位移 <1px |
| 斜坡长度 | `steps * 0.5`，夹在 [4, 12] | 5 帧斜坡被内核合并后只剩两级台阶；10 帧才读得出完整加速段 |
| 帧间隔 | `step_delay = 0.014`，按序号绝对排程 | 抖动只作用于位移/压力，不加到时间轴上（否则相位漂移） |
| force 曲线 | 0.35 → 0.85（前 30% 帧）→ 抬指前放松至 0.45 | 真机按压→放松 |
| radius 曲线 | `4 + 9 * force` | 接触面积随压力变化 |
| 抖动 | force ±0.03、radius ±0.6px、位移 ±0.35px × `min(1, mean_dy/20)` | 位移抖动按当前帧速缩放，不盖过起步段差异 |

**内核 touchmove 合并是这条剖面最大的约束**。`main_thread_event_queue.cc` 的 `kDefaultAsyncTouchMoveInterval = 200ms`（可被 `kAsyncTouchMoveThrottleTimeMs` 开关覆盖）会把 `IsAsyncTouchMove`（`moved_beyond_slop_region && !OriginallyCancelable`）的移动合并到每帧一条。CDP 注入的触摸恰好落在该路径上，实测后果：

- **帧间隔**：首次拖拽按 60fps 一条（`timeStamp` 差 16.7ms），第二次起落到「每两帧一条」（33ms）。两档都是真机采样档，故断言放宽到 8~40ms，只拦同帧连发（<8ms）。
- **位移**：亚像素级的起步帧被合并掉。verify 环境视口高 ~2000px，`dy=600` 的行程下自动步数约 20，此时 10 帧斜坡合并后 `dy ≈ [-20, -24, -27, -31, -34, -38, -38, ...]`，加速段清晰可读。
- **发送侧无法消除合并**：用 rAF 对齐发送、或先等两帧再起手，都会把整段推进到 33ms 档；按 33ms 发送则斜坡在页面上被摊平。

**回归（`scripts/mobile_launch_verify.py`，新增 5 项）**：起步加速段存在（首帧位移 ≤ 匀速段的 75%，且 `dy` 至少 4 个不同值）/ 位移覆盖完整行程（首末 `clientY` 差 > 100）/ `timeStamp` 间隔落在 8~40ms / `force` 随按压起伏（至少 5 个不同值，且 `0 < min < max <= 1`）/ 松手后 `scrollY` 继续增长 ≥ 20px。**套件计数**：Android 150、iOS Safari 181、iOS Chrome 196、数据层 251 全绿。

### 2.14 触控工厂：`createTouch` / `createTouchList` 与 WebKit `Touch` 面（2026-10-20 第九批）

**背景**：iOS 上 `document.createTouch` / `document.createTouchList` 是 WebKit 独有的 legacy 工厂（Chromium 早已移除），此前注入层给了一版实现，但形状是 Chromium 口径——一处 `typeof Touch.prototype.webkitForce` 就穿。本批按 WebKit 真机实测把整条链路（工厂 → 返回值 → 三个接口原型）重做，并在 verify 里补 9 项断言 + 1 项 Android 反向断言。

**WebKit 真机口径**（Playwright WebKit 27.2 实测，`/tmp` 一次性探针）：

| 面 | 取值 |
| --- | --- |
| 工厂挂载 | `Document.prototype` 上的数据属性，描述符 `[writable true, enumerable true, configurable true]`，`length 0`，`name` 为方法名 |
| `Touch.prototype` | `constructor, clientX, clientY, screenX, screenY, pageX, pageY, target, identifier, webkitRadiusX, webkitRadiusY, webkitRotationAngle, webkitForce`——**只有 webkit 前缀，无无前缀同名成员** |
| `TouchList.prototype` | `constructor, length, item` |
| `TouchEvent.prototype` | `constructor, touches, targetTouches, changedTouches, ctrlKey, shiftKey, altKey, metaKey` |
| 构造性 | `new Touch({})`、`new TouchList()` 均 `TypeError: Illegal constructor`；`new TouchEvent('x')` 可构造 |
| 全参回读 | 九项全部生效，四维触控量落在 `webkitRadiusX 5` / `webkitRadiusY 6` / `webkitRotationAngle 45` / `webkitForce 0.75`；`'force' in t === false` |
| 实例形状 | 无自有属性（`Object.getOwnPropertyNames(t) === []`）、`instanceof Touch`、`[object Touch]` |
| 无 target 调用 | `target` 为 `null`，`identifier/pageX/pageY` 为 0，`webkitForce` 为 0 |
| 参数强制转换 | 字符串按数值语义转换（`'7'` → 7）；负 `force` 原样保留 |
| `createTouchList` | 索引与 `item()` 返回同一对象；`item(-1)` 与越界均为 `null`；空列表 `length 0` |

**实现要点**（`app/mobile_cdp_injector.py` block 12，整块在 `if (D.ios)` 内）：

1. **模板实例用合成 touchstart 取**：Chromium 的 `new Touch` 不接受 `target: null`，且产出的实例是 Chromium 形状，不能当模板。改为派发一条合成 `touchstart`、在监听器里抓内核自己造的真 `Touch` 当模板。
2. **无前缀成员删除前先存 getter**：`radiusX` / `radiusY` / `rotationAngle` / `force` 四个成员从 `Touch.prototype` 上删掉，但先存下它们的原生 getter，映射成 `webkit*` 的取值来源——否则页面上真机触摸事件读到的 `webkitForce` 全是 0（P2-4 的拖拽断言当场炸过）。
3. **取值走 WeakMap**：`__mkTouch` 把九项值写进 WeakMap，原型上的 getter 统一从 WeakMap 读，缺省回落到原生 getter / 常量 0。这样实例保持无自有属性，读值又可控。
4. **原型顺序重建**：三个接口的成员顺序是 WebKit 口径的一部分（`Object.getOwnPropertyNames` 直接可比），用 `__reorderProto` 按上面的序列表整体重挂。`configurable:true` 让这一步可行。

**已知残余**：`Touch.length` 在 Chromium 上是 1、WebKit 上是 0，描述符 `[writable false, configurable false]`，运行时改不动。检测站若专门比这一项仍可命中，但单点权重极低，记为不可修残余。

**回归（`scripts/mobile_launch_verify.py`，新增 9 + 1 项）**：工厂存在与描述符 / `length`·`name`·原生外观 / 两个构造器不可构造 / `Touch.prototype` 的 WebKit 成员集与顺序 / 全参回读（九项取值 + 无前缀成员缺席）/ 返回真 `Touch` 实例（无自有属性、`instanceof`、`[object Touch]`）/ 无参调用默认值 / 字符串强转 / `createTouchList` 索引与 `item()` 同源、越界 `null` / 坏 receiver 抛 `TypeError`；另加 **Android 反向断言**——`createTouch`/`createTouchList` 为 `undefined`、`Touch.prototype` 带无前缀 `force` 且无 `webkitForce`，防止 iOS 补丁误挂到 Android 口径。**套件计数**：Android 151、iOS Safari 190、iOS Chrome 205、数据层 251 全绿。

### 2.15 输入层「内核级触摸化」：CDP 鼠标 → 触摸翻译代理（P2-3，2026-10-20 第十批）

**背景**：本项目的 click / scroll 早就走触摸（`app/mobile_input.py`），但那只覆盖自家 API 与 RPA 引擎。外部自动化（Selenium / Puppeteer / Playwright）直连 `ws_endpoint` 时仍会发 `Input.dispatchMouseEvent`——页面上留下 `pointerdown:mouse` / `mousedown` / `wheel` 这些手机不存在的序列，是「手机壳桌面输入」最直接的证据。修复前 verify 里那条「鼠标点击应答正常」的探针，读到的正是这种桌面序列。

**方案**：新增 `app/cdp_input_proxy.py`，在调试端点前挂一层 WebSocket 代理（仅回环地址、仅移动端环境）。客户端连代理、代理连内核，消息逐字转发；只有 `Input.dispatchMouseEvent` 被就地翻译：

| 鼠标命令 | 触摸序列 | 说明 |
| --- | --- | --- |
| `mousePressed`（左键） | `touchStart` | 点击 / 拖拽 / 长按的起点；按住时长原样保留，长按由内核原生触发 |
| `mouseMoved`（按住） | `touchMove` | 按住移动 = 拖拽，松手时内核按速度发起原生 fling |
| `mouseMoved`（未按住） | 丢弃 | 触屏没有 hover；转发反而制造 `mousemove` |
| `mouseReleased` | `touchEnd` | — |
| `mouseWheel` | `touchStart` + 若干 `touchMove` + `touchEnd` | 触屏没有滚轮；滚量换算成一次单指拖拽（与 `mobile_input.scroll` 同一条速度剖面） |
| 中键 / 右键 | 原样放行 | 触摸没有等价语义，不臆造 |

内核会按真机规则自行补齐兼容鼠标事件与 `pointerType=touch` 的 click，所以翻译后的页面序列与真实触摸一致（verify 断言直接比对事件序列）。

**四个实测坑**（都写进了模块注释）：

1. **内核吞鼠标命令的应答**。`Emulation.setEmitTouchEventsForMouse` 的转换路径会吞掉 `mousePressed` / `mouseReleased` 的 CDP 应答，Playwright 的点击永久挂起。代理因此对每条鼠标命令**自己回包**（`{"id": …, "result": {}}`），与内核处理触摸命令的先后无关。
2. **回包必须带回 `sessionId`**。扁平化会话按 `sessionId` 路由应答，丢了会落到根会话、按「未知 id」断言崩溃（Playwright `CRSession` 实测）。
3. **合成命令用独立 id 号段**（`1 << 28` 起）。客户端命令 id 都是小整数，错开即可避免撞号；撞号会让代理吞掉客户端自己的应答。号段必须落在 int32 内——超过 2³¹ 内核直接回 `Message must have integer 'id' property`。迟到的合成应答（等待超时后到达）也要按号段全部吞掉，漏一条就会以陌生 id 上行、把客户端打崩。
4. **既非应答也非事件的上行帧**（内核的解析错误等）必须丢弃，转发同样会让客户端断言崩溃。

**接线**（`app/launcher.py`）：移动端环境建立仿真会话后，把 `info["ws_endpoint"]` 换成代理地址，原地址留在 `info["ws_endpoint_direct"]`（verify 的断线自愈用例直连后者）。桌面环境不挂——鼠标就是桌面输入，翻译反而失真。

**回归（新增 4 项）**：鼠标点击 → `touchstart` + `pointerdown:touch` / 不产生 `pointerdown:mouse` / 滚轮 → 触摸拖拽（`scrollY` ≥ 100px，且事件流含 `touchstart`·`touchmove`）/ 不产生 `wheel` 事件。**套件计数**：Android 158、iOS Safari 198、iOS Chrome 213、数据层 251 全绿。

### 2.16 安全区 `env()` 计算值（P2-5 后半）与传感器读数 60Hz（P2-10，2026-10-20 第十一批）

#### 2.16.1 `env(safe-area-inset-*)`

**背景**：P2-5 前半（`CSS.supports` 与 `-webkit-touch-callout`）已实施，后半一直按「`env()` 属壳能力、补了更容易出错」留作缺口。缺口成立：真机 iOS 上 `env(safe-area-inset-top)` 读 47~62px，本内核恒 0——两个值在同一台机器上并排出现，即可反推「浏览器跑在非 iOS 壳里」。内核 148 已提供 CDP `Emulation.setSafeAreaInsetsOverride`（experimental），本批按真机口径接上。

**内核语义（实测，不是文档推断）**：

| 行为 | 实测结果 |
| --- | --- |
| 未下发 / `insets: {}` | `env()` 与 `env(x, fallback)` 都读 **0px**（文档说未设置的变量变 undefined，实际不成立） |
| 下发后 | 四个方向 + `*Max` 全部生效；缺省字段读 0 |
| 与 `viewport-fit` 的关系 | **无关**——cover 页面和普通页面读数相同。真机 WebKit 只在 `viewport-fit=cover` 下避让，所以「何时下发」必须由我们自己按 meta 决定 |
| 跨导航 | 同一 target 内持久（导航后仍生效），因此每次主框架导航都要重新判定 |
| 已加载文档 | 就地生效（无需刷新） |
| OOPIF | **不传播**——跨域 iframe 的 `env()` 仍为 0（真机 iframe 同样读 0，故不补） |

**实现**（`app/mobile_cdp_injector.py`）：

- 机型口径表 `_IOS_SAFE_AREA_TOP`（CSS 宽 → top）：375→44、390→47、393→59、402→62、414→47、420→59、428→47、430→59、440→62；底部统一 34；iPhone SE（375×667）0/0；iPad 24/20（**不确定项**，真机按 iPadOS 版本/分屏有差异，见下）。
- `derive_spec` 只对 iOS 产出 `safeArea`；Android 恒为空（真机 Chrome 无安全区，verify 反向断言）。
- 挂载：attach 时先清空；每个主框架导航后在 0 / 30 / 120ms 三个时点、以及 `DOMContentLoaded` 时读一次页面 viewport meta，含 `viewport-fit=cover` 才下发（`*Max` 与 inset 同值），否则保持 0。
- **为什么要点位重试**：本内核没有可靠的「meta 解析前」钩子（`Runtime.addBinding` 装不进新文档、`consoleAPICalled` 不投递、`frameNavigated` 晚于 head 脚本），head 内联脚本可能读到 0。真机 Safari 的 `env()` 也在 meta 解析后才定型，这一时序与真机同向。

**已知不确定**：iPad 的 24/20 来自机型归纳而非逐版本真机采样（iPadOS 分屏/台前调度下安全区会变），列为待校准项；`*Max` 目前与 inset 同值，真机上两者在「横屏隐藏 Home 指示条」等场景可能不同。

**回归（iOS 新增 4 项 / Android 1 项）**：cover 页面 `env()` == 机型口径（top/bottom）/ 普通页面 `env()` == 0（WebKit 只在 cover 下避让）/ 二次导航后不残留（与首次一致）/ `safe-area-max-inset-*` 与 inset 同值；Android 反向断言恒 0。

#### 2.16.2 传感器读数刷新率 20Hz → 60Hz

**背景**：事件流本身是内核 60Hz 派发的，但读数每 50ms 才更新一次（名义 20Hz + 40% 抖动）——`deviceorientation` 按「读数变化」派发，页面上看到的是 ~20Hz 的采样率，配合 `devicemotion` 的 `interval=16` 就自相矛盾。

**改造**（`_SensorSimulator` / `_sensor_loop`）：

| 项 | 旧 | 新 |
| --- | --- | --- |
| 名义周期 | 50ms（20Hz） | 16.7ms（60Hz，±20% 抖动） |
| 每步随机游走幅度 | 固定 | 按 tick 缩放（`tick / 0.05`），物理漂移速率（°/s、m/s²/s）不变 |
| 排程 | 发完再 `sleep(周期)` | 绝对时刻排程；落后超过一个周期才重新对齐（避免追帧风暴） |
| 五类读数下发 | 串行 await | `asyncio.gather` 并发（每 tick 5 条命令） |

**为什么必须用绝对时刻**：`sleep(16.7ms)` 在 macOS 上实测每轮多睡 1~2ms，发完再睡会把更新率拖到 ~54Hz；绝对时刻排程把误差吃掉。

**实测（Android，1.5s 观测窗，三次运行）**：`devicemotion` 恒 89 条（内核 60Hz 轮询，`interval=16`）；`deviceorientation` 58~68 条，相邻事件间隔中位数 **17.1~17.2ms**、p90 34~50ms、max 50~84ms——中位数即 60Hz 档，长尾来自事件循环偶发停顿与内核按帧合并（两者真机同样存在，也正好让间隔分布不是精确周期）。

**回归（Android 新增 2 项）**：orientation 1.5s ≥ 45 条（明显高于 20Hz 档）/ 间隔中位数 ≤ 20ms。计数会被停顿成片拉低（实测同一实现 58~68 条），故只用中位数锁采样周期——它能区分「40Hz 稳定」与「60Hz 带停顿」，单看计数分辨不出。iOS 未授权时零事件，不适用。

## 5. 附录：事件层内核缺陷实证（为什么禁用 emit-touch）

对 fp-chromium 148 做 2×2 对照（`scripts/mobile_bigtech_probe.py` 同源方法，直接读 CDP 应答与页面事件序列）：

| 配置 | CDP 鼠标命令应答 | 页面事件序列 | 结论 |
| --- | --- | --- | --- |
| `setEmitTouchEventsForMouse(mobile)` | `mouseMoved` 正常；**`mousePressed/Released` 无应答（永久挂起）** | `pointerdown:touch → touchstart → pointerup:touch → touchend`（**缺**兼容鼠标事件与 `click`） | 会导致 Playwright 点击挂起，且序列不完整：不可用 |
| 关闭该开关 | 全部正常 | 桌面鼠标序列（`pointerdown:mouse / mousedown / …`） | 仅适合桌面目标 |
| `setEmitTouchEventsForMouse(desktop)` | `mouseMoved` 正常；`press/release` 挂起 | 同 mobile 配置 | 不可用 |
| `Input.dispatchTouchEvent`（触摸派发） | 全部正常 | 完整真机序列（触摸 + 兼容鼠标事件 + `click:touch`） | **采用此路径**（`app/mobile_input.py`） |

> `page.touchscreen.tap` 在 `connect_over_cdp` 的默认上下文不可用（`hasTouch must be enabled on the browser context`），因此移动端自动化统一走 CDP 触摸派发；verify 脚本对「鼠标命令应答正常」保留守卫断言，防止将来有人打开 emit-touch 开关造成点击挂起。
